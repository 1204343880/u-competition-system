# InnoTrack 配置服务器总结

本文记录本次 InnoTrack 服务器部署、配置、排障和验证流程。当前部署方式是：

```text
本地编译 JAR
-> scp 上传到服务器
-> 服务器 Docker Compose 重建 app 容器
-> 查看日志和接口验证
```

这套方式适合 2C2G 这类资源紧张的学生服务器：服务器只负责运行容器，不在服务器上跑 Maven、npm 或本地大模型。

## 一、部署目标

目标不是简单把文件传上去，而是形成可验证的上线闭环：

```text
1. 本地代码能编译出 JAR
2. 服务器收到新 JAR
3. app 镜像重新构建
4. app 容器重新创建并读取新环境变量
5. Spring Boot 日志出现 Started RuoYiApplication
6. Nginx 能代理前端和后端接口
7. 核心接口能通过 curl 或浏览器访问
```

## 七、问题 1：YAML 缩进错误

### 现象

`application-docker.yml` 中出现：

```yml
        concurrency: 1
         max-concurrency: 3
```

`max-concurrency` 前面多了一个空格。

### 风险

YAML 依赖缩进表达层级。同级字段缩进不一致，可能导致 Spring Boot 配置解析失败或配置不生效。

### 正确写法

```yml
        concurrency: 1
        max-concurrency: 3
```

### 验证

```powershell
git diff --cached -- Innotrack-competition/innotrack-admin/src/main/resources/application-docker.yml
```

确认暂存区里没有错误缩进。

## 八、问题 2：AGENT_SHARED_SECRET 缺失

### 现象

后端启动失败，日志出现：

```text
Could not resolve placeholder 'AGENT_SHARED_SECRET'
Error creating bean with name 'agentController'
```

### 根因

新 JAR 中 Agent Controller 依赖配置：

```text
AGENT_SHARED_SECRET
```

但服务器 `.env` 和 app 容器环境变量中没有提供。

### 修复步骤

先在服务器 `.env` 中增加：

```bash
cd /opt/competition/RuoYi-Vue-master
echo 'AGENT_SHARED_SECRET=<你的Agent密钥>' >> .env
```

然后在 `docker-compose.yml` 的 `app.environment` 中增加：

```yml
      AGENT_SHARED_SECRET: ${AGENT_SHARED_SECRET}
```

最终 app 环境变量段应该类似：

```yml
  app:
    build: .
    container_name: ruoyi-app
    restart: always
    expose:
      - "8080"
    depends_on:
      - mysql
      - redis
      - rabbitmq
    environment:
      SPRING_PROFILES_ACTIVE: druid,docker
      MYSQL_PASSWORD: ${MYSQL_PASSWORD}
      REDIS_PASSWORD: ${REDIS_PASSWORD}
      MQ_PASSWORD: ${MQ_PASSWORD}
      AGENT_SHARED_SECRET: ${AGENT_SHARED_SECRET}
      JAVA_OPTS: -Xms256m -Xmx512m -XX:MetaspaceSize=128m -XX:MaxMetaspaceSize=256m
```

重新创建 app：

```bash
docker compose up -d --force-recreate app
```

### 验证

```bash
docker inspect ruoyi-app | grep -n "AGENT_SHARED_SECRET"
docker logs ruoyi-app --tail 200
```

## 九、问题 3：RabbitMQ 认证失败

### 现象

日志出现：

```text
AmqpAuthenticationException
ACCESS_REFUSED - Login was refused using authentication mechanism PLAIN
Failed to start bean 'org.springframework.amqp.rabbit.config.internalRabbitListenerEndpointRegistry'
```

### 根因分类

RabbitMQ 认证失败要分两层查：

```text
1. RabbitMQ 内部 admin 用户密码是否正确
2. app 容器是否拿到了正确 MQ_PASSWORD
```

本次排查发现：

```bash
docker exec ruoyi-rabbitmq rabbitmqctl authenticate_user admin '<MQ_PASSWORD>'
```

返回：

```text
Success
```

说明 RabbitMQ 服务端密码正确。

但：

```bash
docker inspect ruoyi-app | grep -n "MQ_PASSWORD"
```

没有输出，说明 app 容器没有拿到 `MQ_PASSWORD`。

进一步检查 `docker-compose.yml`：

```bash
sed -n '60,70p' docker-compose.yml
```

发现 app 的 environment 缺少：

```yml
      MQ_PASSWORD: ${MQ_PASSWORD}
```

### 修复步骤

编辑：

```bash
nano docker-compose.yml
```

在 app 的 `environment` 下补齐：

```yml
      MQ_PASSWORD: ${MQ_PASSWORD}
```

保存 nano：

```text
Ctrl + O
回车
Ctrl + X
```

强制重建 app：

```bash
docker compose up -d --force-recreate app
```

### 验证

```bash
docker compose config | grep -n "MQ_PASSWORD\|AGENT_SHARED_SECRET"
docker inspect ruoyi-app | grep -n "MQ_PASSWORD"
docker logs ruoyi-app --tail 200
```

成功后不应再出现：

```text
ACCESS_REFUSED
Authentication failure
```

## 十、问题 4：RabbitMQ 密码和 .env 不一致

### 现象

`.env` 中配置了：

```text
MQ_PASSWORD=<你的MQ密码>
```

但 app 仍然 RabbitMQ 认证失败。

### 原因

RabbitMQ 使用 Docker volume 持久化后：

```text
RABBITMQ_DEFAULT_USER
RABBITMQ_DEFAULT_PASS
```

只在容器第一次初始化数据目录时生效。

后续只改 `.env`，不会自动修改 RabbitMQ 已存在用户密码。

### 修复

把 RabbitMQ 内部 `admin` 用户密码改成 `.env` 中的 `MQ_PASSWORD`：

```bash
docker exec ruoyi-rabbitmq rabbitmqctl change_password admin '<你的MQ密码>'
docker exec ruoyi-rabbitmq rabbitmqctl set_permissions -p / admin ".*" ".*" ".*"
docker exec ruoyi-rabbitmq rabbitmqctl authenticate_user admin '<你的MQ密码>'
```

看到：

```text
Success
```

说明 RabbitMQ 侧密码正确。

## 十二、问题 6：`.env` 和容器环境变量不是一回事

`.env` 只是给 Docker Compose 做变量替换。

例如 `.env` 有：

```text
MQ_PASSWORD=<你的MQ密码>
```

并不代表 app 容器里一定有：

```text
MQ_PASSWORD
```

必须在 `docker-compose.yml` 的 app 服务中显式声明：

```yml
environment:
  MQ_PASSWORD: ${MQ_PASSWORD}
```

然后重新创建容器：

```bash
docker compose up -d --force-recreate app
```

验证容器环境变量：

```bash
docker inspect ruoyi-app | grep -n "MQ_PASSWORD"
```

## 十四、什么时候需要重启 MySQL / Redis / RabbitMQ

大多数业务代码更新只需要重启 app：

```text
Controller / Service / Mapper 改动 -> 重启 app
RabbitMQ 生产者 / 消费者代码改动 -> 重启 app
application-docker.yml 中 app 读取的配置改动 -> 重启 app
```

不需要重启基础设施容器。

只有以下情况才考虑动基础设施：

```text
MySQL 容器端口、密码、字符集、my.cnf、volume 改动 -> 可能需要重启 MySQL
Redis 密码、内存策略、volume 改动 -> 可能需要重启 Redis
RabbitMQ 用户、密码、插件、volume、端口改动 -> 可能需要重启 RabbitMQ
```

数据库表结构变更不是靠重启 MySQL 解决，而是靠迁移 SQL：

```bash
docker exec ruoyi-mysql mysqldump -uroot -p'<MYSQL_PASSWORD>' ruoyidemo > backup_before_deploy.sql
docker exec -i ruoyi-mysql mysql -uroot -p'<MYSQL_PASSWORD>' ruoyidemo < 增量脚本.sql
```

## 十五、当前故障定位顺序

如果 app 启动失败：

```text
1. docker logs ruoyi-app --tail 200
2. 找 Caused by
3. 判断是配置缺失、DB、Redis、RabbitMQ、代码异常
4. 修配置或服务状态
5. docker compose up -d --force-recreate app
6. 再看日志和接口
```

不要先猜数据库，也不要看到 500 就直接重启所有容器。

## 十七、后续改进建议

当前缺少 `AGENT_SHARED_SECRET` 会导致主系统启动失败。后续可以考虑：

或给非生产环境默认值，避免 Agent 增强功能拖垮主业务。

### 2. MQ 消费者失败降级

```text

```

如果只是通知链路，应该允许主业务启动，并在 MQ 不可用时降级或记录告警。

### 3. 增加版本证明

后续可以在启动日志或接口中输出：

```text
git commit
build time
version
```

用于证明线上运行的是新 JAR。

### 4. 固化部署脚本

把手工步骤沉淀为脚本：

```text
build jar

rebuild app
tail logs
curl health check
```

减少手敲命令导致的配置遗漏。

## 十八、问题 7：公网访问页面还是旧系统

### 现象

后端 JAR 已经上传，`app` 容器也重新构建/重启，但浏览器访问公网：

```text
http://服务器IP/
```

页面看起来仍然和原来系统一模一样。

### 根因

本次只更新了后端 JAR：

```text
ruoyi-admin.jar
app 容器
后端配置
RabbitMQ / Agent 相关环境变量
```

但公网首页不是直接由 JAR 决定，而是由 Nginx 服务的前端静态文件决定。

服务器 `docker-compose.yml` 中 nginx 类似这样挂载：

```yml
nginx:
  image: nginx:alpine
  container_name: ruoyi-nginx
  ports:
    - "80:80"
  volumes:
    - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    - ./ruoyi-ui/dist:/usr/share/nginx/html:ro
  depends_on:
    - app
```

这代表：

```text
浏览器访问 http://服务器IP/
-> 命中 nginx:80
-> nginx 读取 /usr/share/nginx/html
-> 该目录来自服务器 ./ruoyi-ui/dist
```

所以如果服务器上的：

```bash
/opt/competition/RuoYi-Vue-master/ruoyi-ui/dist
```

没有更新，页面就一定还是旧页面。

### JAR 包里不是也可能有前端吗？

可能有，但当前公网链路优先走 Nginx。

即使 JAR 里打进了 `static/index.html`，当前部署也不是让浏览器直接访问 app 容器的静态资源：

```text
app 容器只 expose 8080
没有直接对公网发布 8080
公网 80 端口由 nginx 容器提供
nginx 的 / 路径服务的是 ./ruoyi-ui/dist
nginx 的 /prod-api 才反向代理到 app:8080
```

因此：

```text
更新 JAR -> 更新后端接口和后端逻辑
更新 dist -> 更新公网前端页面
```

这不是“反向代理导致前端没更新”，更准确地说是：

```text
Nginx 的静态资源挂载路径决定了公网首页来自服务器 dist，而不是来自 JAR。
```

反向代理只负责把 `/prod-api` 这类接口请求转发给后端。

### 验证前端是否更新

服务器执行：

```bash
cd /opt/competition/RuoYi-Vue-master
stat ruoyi-ui/dist/index.html
ls -lh ruoyi-ui/dist
```

如果 `Modify` 时间还是旧的，说明前端 dist 没上传。

也可以看 Nginx 配置：

```bash
grep -n "root\|proxy_pass\|/prod-api" nginx/nginx.conf
```

典型逻辑：

```text
/         -> nginx 静态 dist
/prod-api -> proxy_pass 到 app:8080
```

### 正确前端更新流程

本地 Windows 先构建前端：

```powershell
cd D:\code\cursor_code\RuoYi\Innotrack-competition\innotrack-ui
npm run build:prod
```

确认本地生成：

```powershell
dir .\dist
```

上传到服务器：

```powershell
scp -r .\dist root@服务器IP:/opt/competition/RuoYi-Vue-master/ruoyi-ui/
```

服务器重启 Nginx：

```bash
ssh root@服务器IP
cd /opt/competition/RuoYi-Vue-master
docker compose restart nginx
```

浏览器强刷：

```text
Ctrl + F5
```

或者用无痕窗口访问，排除浏览器缓存。

### 更稳的前端部署方式

先备份旧 dist：

```bash
cd /opt/competition/RuoYi-Vue-master
cp -r ruoyi-ui/dist ruoyi-ui/dist_backup_$(date +%Y%m%d_%H%M%S)
```

再上传新 dist。

如果上传后出现白屏，可以回滚：

```bash
rm -rf ruoyi-ui/dist
mv ruoyi-ui/dist_backup_具体时间 ruoyi-ui/dist
docker compose restart nginx
```

### 验证前后端分别是否更新

后端是否更新，看：

```bash
stat ruoyi-admin.jar

```

前端是否更新，看：

